You are a coding agent working on the NARU repository

Attached reference: `opencode-tools.json` (the exact 10 tool schemas opencode 1.18.35 sends to the model).

## Ground rules

- Compare both agents **as shipped**, with their default agent config. Do not tune either system prompt.
- Do not modify NARU core behavior. Phase 1 is read-only plus running probes. If you need glue (a headless launcher, a `.naru` routine), put it under `bench/` and say so.
- Everything you claim must come from something you ran or read. Mark anything unverified as `UNVERIFIED`.
- Run benchmark runs **sequentially**, never in parallel (GPU fairness, clean timing, clean attribution).
- Isolate each agent's global state (use a throwaway `HOME`/`XDG_*` for opencode; a throwaway user-level `.naru` scope for NARU) so personal AGENTS.md, skills, or agent files do not leak into runs.

## Phase 0: preflight (stop and report if any item fails)

1. **Models.** Matrix below. Run a 1-token completion against each endpoint.
   - `ollama/qwen3.8:latest`: check `ollama list` / `ollama show`. If the tag does not exist, stop and report what is installed. Do not substitute silently.
   - `gemini-2.5-flash`: **Google's announced shutdown for this model on the Gemini Developer API is 2026-10-16, and some users already report 404s.** If the 1-token call returns 404, stop and ask which replacement to use (`gemini-3.5-flash` is the documented successor). Keep model IDs in one config file so swapping is a one-line change.
2. **Ollama context window trap.** Ollama's OpenAI-compatible endpoint ignores per-request `num_ctx`. opencode alone sends roughly 30 KB (about 8k tokens) before the task starts, which overflows small default contexts and **silently truncates** the prompt. Create a derived model via Modelfile (`PARAMETER num_ctx 32768`, or whatever fits the GPU) or set `OLLAMA_CONTEXT_LENGTH`, and verify with `ollama ps` (CONTEXT column). Use the same effective context for both agents.
3. **Thinking mode.** Determine whether each model emits reasoning/thinking tokens. Set thinking identically for both agents (both on, or both off) and write down which. Record reasoning tokens separately when the API reports them.
4. **Protocol normalization (default).** Use the **OpenAI-compatible chat-completions wire format for both agents and both models** (Ollama `/v1`, Gemini `https://generativelanguage.googleapis.com/v1beta/openai/`). This removes serialization differences between native protocols from the comparison. Native-protocol runs (NARU supports Ollama native and Gemini native) are an optional extra at the end.

## Phase 2: measurement layer

Measure **at the HTTP boundary, identically for both agents**, using upstream-reported `usage`, never your own tokenizer estimates.

**Default: `bench/teeproxy.py`** (Python 3 stdlib only, about 100 lines).
- Listens on one local port; the first path segment is the **run id**: clients use `baseURL = http://127.0.0.1:<port>/<run-id>/v1`. This tags runs without relying on custom headers.
- Forwards to the configured upstream (injects the upstream API key itself; the agents get a dummy key).
- Appends one JSON line per request to `bench/data/<run-id>.jsonl`: timestamps, latency, status, request body (full), response (SSE reassembled: final text, `tool_calls` names and arguments, `usage` including cached/reasoning details when present), request/response byte sizes.
- Must handle streaming SSE without buffering the whole response before forwarding.
- Classify each request: `main` (has tools), `title` (no tools, system prompt starts with "You are a title generator"), `other`.

Optional cross-checks (nice to have, not required): (a) NARU's own metering (`NaruMeteringService`, `NaruModelStats`) versus proxy totals; large drift means a metering bug worth filing. (b) NARU's `task-<id>.tson` request logs. (c) Bifrost in front of the tee proxy for a second count.

## Phase 4: runner (`bench/run.py`)

For each `(agent, model, task, run_index)`:
1. Fresh temp dir; copy fixture; `git init` and commit; start the task's side services (T5 server).
2. Start a fresh run id; point the agent's baseURL at the tee proxy.
3. Run headless with identical constraints:
   - **opencode**: `opencode run --auto --format json -m <provider/model> ... < /dev/null` with `OPENCODE_DISABLE_AUTOUPDATE=1` and `OPENCODE_DISABLE_AUTOCOMPACT=1` (compaction is off for fairness, since NARU has no compaction yet; keep tasks short enough that context never overflows). Notes from testing 1.18.35: stdin must be closed or redirected or `run` hangs reading it; `run` wraps a multi-word positional prompt in literal quotes, so check the proxy log to confirm what text arrived and, if needed, pass the prompt via stdin to keep it byte-identical; `ask` permissions are auto-rejected in headless mode, hence `--auto`.
   - **NARU**: find its non-interactive entrypoint (`app/naru` `NaruApp`, routines). If none exists, write the thinnest possible launcher under `bench/` that submits the prompt and exits when the agent loop ends. Enable the tag/tool grants identified in Phase 1 (the equivalent of `--auto`).
   - Same model, same temperature (set explicitly, 0 where supported), same effective context, same thinking setting, working dir = the temp dir.
   - Caps: wall clock (Ollama 20 min, Gemini 10 min) and max `main` requests (default 60). Hitting a cap = fail, record why. Retries on 429/5xx are allowed; count attempts and successes separately.
4. Run `accept.sh`; capture `git diff --stat` and the final answer text.
5. Write `bench/results/<run-id>.json`:
   `agent, agent_version (opencode version / NARU git sha), model, task, run_index, pass, accept_output, wall_s, exit_code, hit_cap, requests_{main,title,other}, attempts_failed, prompt_tokens, completion_tokens, reasoning_tokens, cached_prompt_tokens, peak_prompt_tokens_single_request, tool_calls_by_name, request_bytes_total, files_changed, lines_added, lines_removed, final_text`.

Repetitions: **5 per cell for Ollama, 3 for Gemini** (stochastic; a single run is an anecdote). Order runs interleaved by agent (A, B, A, B...) so drift (thermal, rate limits, time of day) hits both equally.

## Phase 5: analysis (`bench/REPORT.md`)

Per `(task, model)`: pass rate for each agent; median, min, max of total prompt tokens, completion tokens, reasoning tokens, main requests, tool calls, wall time; NARU/opencode ratios. Also:
- T0 overhead for each agent, plus the **marginal** cost of each task (task tokens minus the part explained by repeated overhead; show prompt tokens per request index as a CSV/plot to expose context growth).
- Results with and without opencode's `title` call.
- Cached versus uncached prompt tokens (Gemini implicit caching, Ollama KV reuse affect cost and time, not raw counts).
- Quality beyond pass/fail: diff size, tests added, whether the agent verified its work by running tests. If you use an LLM judge, blind it to agent identity.
- Failure analysis: for every failed or capped run, the first point where behavior diverged (wrong tool, malformed tool call, looping, ignoring tool output).

**Decision rule (pre-registered, edit before running if you disagree):** NARU is "comparable" for a (model, task) cell if its pass rate is within 20 percentage points of opencode's **and** its median total billable tokens (prompt + completion + reasoning) is within 0.75x to 1.33x of opencode's.
